# DeepSeek 官方账号登录余额（account-login）

> 目标：用户**用 DeepSeek 官方账号登录**（`deepseek-account-platform`，不是 API Key）时，
> 看板也能显示余额；且绝不因为「读不到」而伪造 0 或假数字。
>
> 改动落在 `dsh-api-dashboard-acct`（v1.7.4 快照）。无新增依赖、无安装脚本、无新落盘文件。

---

## 0. 一句话行为

- 显式 API Key（环境变量 / DSH `credentials` / `.credentials.yaml` 的 `refs:`）**永远优先**。
- 完全没有 key、且平台是 DeepSeek 时，才读 `deepseek-account-platform/default` 的账号 grant，
  请求 `GET {issuer}/api/v0/users/get_user_summary`（`x-dsh-auth-token`），
  解析 `normal_wallets`（充值）+ `bonus_wallets`（赠送），`note` 标明 **「DeepSeek 账号余额」**。
- 读不到 → 既有的 `no-key` / `no-balance-api` / `auth-error` / `error`；不编数字。
- token 只在内存里用一次：不落盘、不缓存、不打印、不进错误文案。

## 1. 凭据怎么读

### 1.1 主路径：DSH `credentials` 服务的 record 接口

```js
const record = await ctx.get('credentials').readRecord('deepseek-account-platform/default')
// → { kind: 'grant', payload: { version, token, issuer } }
```

宿主写入方：`@deepseek-ai/dsh-deepseek-account-platform/lib/index.js`；
`readRecord` 实现：`@deepseek-ai/dsh-credentials-local/lib/index.js:527-529`；
`grant` record 的准入结构：同文件 `:236-263`（只允许 `kind` + `payload`）。

### 1.2 兜底：直接解析 `~/.dsh/.credentials.yaml`

与现有 API Key 的第三层兜底同一个文件、同一个 home（`DSH_HOME` 优先）：

```yaml
version: 1
records:
  deepseek-account-platform/default:
    kind: grant
    payload:
      version: 1
      token: <账号授权 token>
      issuer: https://platform.deepseek.com
```

`parseAccountGrantText()`（`src/index.js:2388`）是一个**只服务于本需求**的极简行解析器：

- 只认顶层 `records:` 段里的 `deepseek-account-platform/default`（2 空格缩进，key 可带引号）；
- 只认 `kind: grant` + `payload:` 下的 `token` / `issuer`；
- 不含 YAML 依赖（零依赖红线），不解析 `refs:`（那是 API Key 段，与账号 grant 无关）；
- 任何不合结构（record 缺失、`kind` 不对、payload 不是块映射、值非法）→ `null`，不抛。

`readAccountGrant()`（`src/index.js:2440`）先试 credentials 服务，服务不可用/无此方法/结构不合法时
再读文件；两条路都拿不到 → `null`。

### 1.3 token 的处置红线

- 只在 `readAccountGrant()` 的返回值里存在，随即作为请求头使用；**不写入缓存对象、状态文件、日志**。
- 所有错误文案都是固定文本 + HTTP 状态码；**不读取非 2xx 的响应体**，也不把 URL / headers / body
  拼进错误（避免服务端回显 token）。
- `normalizeAccountGrant()` 要求 token 是非空可打印 ASCII（`^[\x21-\x7e]+$`，与宿主换取 token 的
  schema 同口径），不接受带空白/换行的值。
- `issuer` 只接受纯 `http(s)://host[:port]` 源：带路径、query、fragment、用户名密码一律视为缺失
  （不猜 `api.deepseek.com` 之类默认域名）。

## 2. 接口与字段依据（宿主源码，不是想象）

宿主包：
`/usr/local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-deepseek-account-platform/lib/index.js`
（下称 `platform/lib/index.js`）。

| 事项 | 依据 |
|---|---|
| 余额端点 | `queries.balance.path = "/api/v0/users/get_user_summary"`（`platform/lib/index.js:402-403`） |
| 请求头 | `accountHeaders()` 只加 `x-dsh-auth-token: <token>`，**没有** `Authorization: Bearer`（`:189-194`） |
| 请求方式 | `requestAccount()` → `GET {origin}{path}`（`:150-156`、`:424-430`） |
| 外层 envelope | `{ code: 0, data: { biz_code: 0, biz_data } }`（zod `envelope`，`:103-110`） |
| 钱包字段 | `wallet = { currency: z.enum(["CNY","USD"]), balance: z.string().regex(数值) }`（`:342-347`） |
| 余额 body | `summary = { normal_wallets: wallet[], bonus_wallets: wallet[] }`（`:349-352`） |
| 授权失效 | HTTP 401（带 `x-dsh-auth-token` 时）→ `AccountUnauthorizedError`（`:238-246`）；业务码 `40003` 同判（`:282`） |
| 客户端身份头 | `platformClientHeaders()` → `x-client-bundle-id` / `x-client-platform` / `x-client-version` / `x-client-locale` / `x-client-timezone-offset`（`@deepseek-ai/dsh-deepseek-account/lib/index.js:68-77`） |

### 2.1 解析实现（`src/index.js`）

1. `accountWalletsToBalanceInfos()`（`:2475`）把两个数组归一成与 `balance_infos` 同构的条目：
   - 充值 `normal_wallets` → `topped_up_balance`
   - 赠送 `bonus_wallets` → `granted_balance`
   - `total_balance` = 两者之和（同币种多次出现则累加；浮点尾巴按 1e-6 取整）
2. `parseAccountResponse()`（`:2508`）校验 envelope 与钱包结构，然后**调用既有的**
   `pickWalletInfo()`（`:2100`，v1.4.2 规则：**主货币优先 → 有余额的 → 首条**）挑选钱包。
   没有另写一套挑选逻辑；`case 'deepseek'` 的 API Key 解析也改用它（行为不变，
   `test-deepseek-multicurrency.mjs` 15 条全绿）。
3. 返回字段：

   ```js
   { total, currency, available: total, used: null, topup, grant, note: 'DeepSeek 账号余额' }
   ```

   - `used: null`：账号接口不提供「已用」口径（没有 `total_usage` / `total_credits`），
     如实留空；客户端现有逻辑 `b.used != null && b.used > 0` 不会渲染它。
   - 查询结果额外带 `source: 'account'`（客户端未消费，但便于诊断 / 后续 UI 标注）。

### 2.2 关于 `x-client-*` 头（**故意不带**）

宿主 `platformClientHeaders()` 发 5 个客户端身份头，其中：

- `x-client-bundle-id` 恒为空串、`x-client-platform` 恒为 `web` —— 这两个是常量；
- `x-client-version` / `x-client-locale` / `x-client-timezone-offset` 来自**发起请求的 UI 客户端**
  （版本号、界面语言、时区偏移秒数）。插件服务端拿不到这些真实值，猜一个等于伪造。

因此本实现**一个 `x-client-*` 都不带**（只带 `Accept` 与 `x-dsh-auth-token`）。
⚠️ 这是本需求最大的未验证点：**如果服务端强校验这些头，真实请求会失败**。
按失败矩阵会落到 `auth-error`（401/403）或 `error`，不会伪造余额。详见 §5。

## 3. 优先级怎么处理

实现位置：`queryPresetWithAccountFallback()`（`src/index.js:2688`），由 `refreshAll()`
的预设查询统一调用（`src/index.js:3778`）。

```
resolvePresetKey(platform) 得到 key
  ├─ key 非空 → queryPreset(key 路径)        ← 账号凭据一次都不读
  └─ key 为空
       ├─ 平台不是 deepseek → queryPreset('') → 既有 no-key
       └─ 平台是 deepseek
            ├─ 懒调用 readAccount()
            ├─ grant 为空 / token 为空 → 既有 no-key
            └─ 有 token → queryDeepSeekAccountPreset()
```

- **`readAccount` 懒调用**：有 key 的用户不会多读一次凭据文件/凭据服务（测试 A5 钉住）。
- **`note` 标明来源**：账号路径固定 `note = 'DeepSeek 账号余额'`，用户能在状态条/详情里看出
  这不是 API Key 那条路（API Key 路径仍是原来的 `'可用余额'`）。
- 只有 DeepSeek 平台有账号回退；其他预设平台完全不受影响。

## 4. 失败矩阵

| 情形 | 返回 `status` | 文案 / 说明 | 是否可能伪造数字 |
|---|---|---|---|
| 无 key、无账号 token / record 缺失 / token 空 | `no-key` | `未配置 API Key`（既有语义） | 否 |
| 有 token 但 `issuer` 缺失或非法 | `no-balance-api` | `DeepSeek 账号凭据缺少 issuer，无法查询账号余额` | 否 |
| HTTP 401 / 403 | `auth-error` | `HTTP <code> (DeepSeek 账号授权未通过，请重新登录账号)` | 否 |
| body `code: 40003` | `auth-error` | `DeepSeek 账号授权已失效，请重新登录` | 否 |
| HTTP 404 / 405 | `no-balance-api` | `HTTP <code> (账号余额接口未开放)` | 否 |
| 其他非 2xx（500 等） | `error` | `HTTP <code>`（不读响应体） | 否 |
| 网络异常 / 超时 | `error` | `网络错误` / `请求超时` | 否 |
| 非 JSON / envelope 不符（`code !== 0`、缺 `data`、`biz_code !== 0`） | `no-balance-api` | `无法解析 DeepSeek 账号余额数据` | 否 |
| `normal_wallets` / `bonus_wallets` 非数组、钱包项非法、金额非法、币种不在 CNY/USD | `no-balance-api` | 同上 | 否 |
| 两个钱包数组都为空 | `no-balance-api` | 同上（**不当作余额 0**） | 否 |
| 结构合法、金额为 `"0.00"` | `ok`，`total: 0` | `DeepSeek 账号余额` | 真 0，如实显示 |

补充：

- `auth-error` 不会触发 `refreshAll` 的 last-known-good 兜底（只有 `status:'error'` 且错误不含
  「认证」才复用旧数据）→ token 失效会**显式变成中性状态**，不会静默沿用旧余额。
- `403` 归 `auth-error` 是**本插件的选择**（与既有 API Key 路径的 401/403 口径一致）；
  宿主的 `platformRequest` 把 403 归为 network failure（`:238-246` 只特判 401）。见 §5。

## 5. 未验证的部分（如实列出）

本环境**没有真实 DeepSeek 账号**、也不允许联网验证，所以以下都是「按宿主源码实现、未实测」：

1. **`x-client-*` 头是否被服务端强校验 —— 未验证。**
   本实现不带任何 `x-client-*` 头（理由见 §2.2）。若服务端强制要求，真实调用会失败；
   失败会落到 `auth-error`（401/403）或 `error`，**不会显示假余额**，但会把「缺少客户端身份头」
   误报成「授权未通过」——错误文案已尽量中性（只说「未通过，请重新登录」，不断言 token 失效）。
   **这是上线前必须用真实账号验证的第一项。**
2. **真实响应体未亲眼观察。** envelope / `biz_code` / 钱包字段结构全部来自宿主 zod schema 与
   `queries.balance.parse`，不是我们在真机上抓的包。若服务端字段漂移，按矩阵走 `no-balance-api`。
3. **`normal_wallets` 与 `bonus_wallets` 是否可相加 —— 未验证。**
   本实现按「充值 + 赠送 = 总余额」求和（需求描述与宿主把两者分列返回的口径）。
   如果平台实际上已把赠送额包含在 `normal_wallets` 里，会**重复计算**。真实账号需对照控制台核对一次。
   若要规避该风险，可改为只显示 `normal_wallets`、把 `bonus_wallets` 放 `grant` 供详情展示
   （当前实现选择了求和 + 分项保留）。
4. **`issuer` 的实际值**：本机凭据文件里是 `https://platform.deepseek.com`，与 API 基址
   `https://api.deepseek.com` 不同；代码严格用 `issuer`（宿主也是 `origin` + path），未在真机验证
   该 origin 上 `get_user_summary` 的可达性。
5. **`used: null` 在详情弹层的视觉表现**未在真机看过；代码层面已确认客户端只在
   `b.used != null && b.used > 0` 时渲染「总使用」。
6. **`note` 的来源提示**沿用既有 note 渲染位（状态条文案 / 详情「类型」），未新增客户端代码，
   因此未做真机视觉验收。
7. **刷新频率下的文件读取开销**：无 key 的账号用户，每次轮询（可低至 1 秒）都会重读一次
   `~/.dsh/.credentials.yaml`（几 KB）或调一次 `readRecord`。未做 token 缓存（缓存会拉长
   token 撤销的生效延迟，权衡后选择每次现读）；未在真机测量开销。
8. **`credentials` 服务的 `readRecord` 不是抽象基类声明的接口**（只在
   `dsh-credentials-local` 实现里存在）。代码用 `typeof === 'function'` 探测，缺失时自动退回文件；
   若未来宿主换 provider 且不提供该方法，读凭据文件仍可用。
9. **v1.7.4 issue #3/#4 的 portal / GLM windows 改动未触碰**；`MODEL_PRICES` / `V4_RATES` 未触碰。
